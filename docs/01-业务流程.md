# 业务流程

公开版把系统拆成九个环节，每个环节都可以替换成自己的实现。

## 1. 生成巡查计划

输入来自产品库。每一条产品计划通常包含：

- 产品名称。
- 规格。
- 厂家或品牌。
- 需要巡查的平台。
- 标题必须命中的关键词。
- 优先级。
- 是否启用。

输出是标准化的 `ProductPlan` 列表。

## 2. 平台候选采集

平台适配器负责把不同来源的搜索结果转换成统一候选记录。公开版不包含真实平台访问实现，只定义输入输出边界。

候选记录包含：

- 平台。
- 商品 ID。
- 商品标题。
- 规格。
- 价格。
- 店铺名称。
- 商品链接。
- 采集时间。

## 3. 字段归一化

不同平台的字段格式差异很大，需要归一化：

- 价格转成统一文本和数值。
- 标题去除营销噪音。
- 链接归一化。
- 商品 ID 提取稳定标识。
- 规格拆分成可比较形式。

## 4. 规则库过滤

规则库用于把不需要进入业务流程的候选记录排除掉。

常见规则类型：

- 自有店铺排除。
- 已知非目标商品排除。
- 同店同品多规格合并或排除。
- 区域例外。
- 临时人工复核名单。

公开版不包含真实规则，只保留规则类别说明。

## 5. 客户库匹配

候选记录只有店铺名时，系统会尝试匹配客户库，补齐企业名称、区域或连锁归属。

匹配方式可以包括：

- 店铺名称精确匹配。
- 店铺名称关键词匹配。
- 企业别名匹配。
- 人工维护的例外映射。

## 6. 人员路由

根据企业、区域、连锁或人工字段，匹配负责的大区、业务员、客服或管理员角色。

公开版建议不要把人员 ID 写进代码，应从安全配置、目录服务或私有表格读取。

## 7. 写入登记表

系统将候选记录写入正式登记表。登记表的关键点是：系统只负责准备记录，是否确认由人来决定。

常见状态：

- `waiting_for_confirmation`：等待人工确认。
- `confirmed`：已确认，进入可推送池。
- `sent`：已推送。
- `retryable_failed`：临时失败，可重试。
- `failed`：不可自动恢复，需要人工处理。

## 8. 确认后推送

真实通知前先执行 dry-run，确认本轮要推送哪些记录、推给哪些角色、是否存在缺失人员。

推送策略：

- 已确认才推送。
- 已推送不重复推送。
- 部分人员缺失时记录缺失原因。
- 推送成功后回写状态。

## 9. 运行摘要与审计

每次运行都应生成 manifest，记录：

- 本轮时间。
- 触发入口。
- 巡查计划数量。
- 候选数量。
- 过滤数量。
- 写表数量。
- 推送数量。
- 错误与告警。

manifest 不应包含敏感 token、Cookie 或真实账号凭据。
